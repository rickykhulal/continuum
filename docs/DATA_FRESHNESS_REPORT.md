## 3. Data Provenance & Freshness Assurance

### How the System Maintains Correct Timestamps

1. **Acquisition timestamps preserved**: 
   - FIRMS CSVs carry original acquisition times (`acq_time` field)
   - `epochSeconds()` converts `acq_date` + `acq_time` to Unix seconds
   - These timestamps flow through `build-data.mjs` → `live_fires.json` → API → frontend
   - Never artificially shifted

2. **Provenance tracking per record**:
   - Each `DailyRecord` carries: `source` (model/archive/live), `provisional`, `trust`, `lo`/`hi`
   - `LiveBundle.meta.windowStart`/`windowEnd` defines the live window
   - Archive days marked `provisional = kindM === 1 || kindV === 1 || kindN === 1 || kindN21 === 1`

3. **API freshness tracking**:
   - `getResponse()` includes `fetchedAt` timestamp
   - `stale` flag when cache expired (10 minutes) but last-good served
   - `liveStatus` in frontend: `'loading' | 'live' | 'stale' | 'offline' | 'not_configured'`

### Stale Data Handling

| Scenario | Behavior |
|----------|----------|
| API running, data fresh | `liveStatus = 'live'`; `freshness = 0 days` |
| API running, data > 10 min old | `liveStatus = 'stale'`; `setIsStale(true)` in UI |
| API not running | `liveStatus = 'not_configured'`; badge shows "live data not configured" |
| API failure (upstream error) | Serve last-good result with `stale=true`; never fabricate data |
| First run, no prior data | `liveStatus = 'offline'`; no data until first fetch completes |
